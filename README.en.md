# Vision Primitives MCP — a vision-primitive MCP server that gives text-only LLMs eyes







[简体中文](./README.md) | [English](./README.en.md)







Give text-only LLMs (like `deepseek-v4-flash`) full "see + manipulate images" capability through MCP tools: **describe → locate (coordinates) → annotate → crop/zoom → OCR** as an interactive loop, with processed images returnable for display.







Vision backend: **Xiaomi MiMo V2.5** (OpenAI-compatible API, fully multimodal, supports image input and coordinate output).







- Implementation: single-file Python (`vision_bridge_mcp.py`), only dependency is Pillow, zero third-party runtime dependencies



- Protocol: hand-written MCP stdio (JSON-RPC 2.0 + Content-Length framing), compatible with Codex desktop/CLI and any MCP client



- Inspired by: HanaAgent's Vision Bridge (auxiliary vision model + structured "vision primitives") + DeepSeek's *Thinking with Visual Primitives* (coordinate boxes/points + labels)







## Tool Overview (24 tools)







| Tool | Purpose | Key params |



|---|---|---|



| `describe_image` | Text description of an image | `image` required; `question`, `detail`(brief/balanced/detailed) |



| `analyze_image` | Structured analysis: description + visual_primitives (box/point + label + confidence) | `image` required; `format`(generic/gemini/qwen) |



| `locate_object` | Locate a target object, return coordinates (LLM outputs coordinates); `refine=true` two-stage refinement | `image`, `target` required; `coords`(pixel/norm), `refine` |



| `som_locate` | **SoM numbered-grid recursive locate**: overlay numbered marks, model answers the number (not coordinates), crop-and-zoom convergence per round | `image`, `target` required; `grid`, `rounds`, `expand` |



| `cursor_locate` | **Cursor-move + visual feedback loop locate**: render cursor, model outputs relative offset (dx/dy) to converge (GUI-Cursor paradigm) | `image`, `target` required; `max_steps`, `step_ratio`, `start` |
| `cv_locate` | **CV precision locate (fallback)**: color segmentation + connected-component centroid (pixel-level, measured 0-4px, zero-dependency) or template matching; for solid-color UI elements / geometric shapes / fixed templates; limited generalization | `image`, `target` required; `color`/`template` at least one; `min_area` |



| `ocr_image` | Per-block OCR with bbox (pixel + normalized) | `image` required; `language` |



| `annotate_image` | Draw boxes/points/labels on image, save annotated image | `image`, `items` required; `coords`, `out_path`, `style` |



| `crop_image` | Crop by coordinates (edge expansion `expand_px` supported) | `image`, `box` required; `coords`, `expand_px` |



| `zoom_region` | Region zoom (scale 1-8) | `image` required; `box`, `scale` |



| `vision_health` | Check backend config and connectivity | — |



| `compare_images` | **Multi-image comparison** (2-4): A/B screenshots, design consistency, multi-frame analysis | `images` required (2-4); `question`, `detail` |



| `compare_infer` | **Multi-image joint reasoning**: each image with independent annotations, reasoning over differences/causality/temporal/overall | `images`, `question` required; `items_per_image`, `mode` |



| `reason_graph` | **Interactive graphical reasoning protocol**: primitives(locate/measure) → semantics(semantic/hypothesis) → annotation(annotate/verify) multi-round loop, session state across rounds | `image`, `step` required; `session`, `question` |



| `screen_capture` | Screen capture (full screen or region), enabling "see the screen" | `region`, `out_path` optional |



| `screen_info` | Screen resolution / DPI / control switch state | — |



| `screen_click` / `screen_move` / `screen_drag` / `screen_scroll` / `screen_type` / `screen_key` | Mouse & keyboard control (requires `VISION_ALLOW_SCREEN_CONTROL=1`) | coordinate/key params |



| `annotate_infer` | **Virtual annotation + graphical reasoning**: boxes/points/lines/arrows/circles/polygons/bubbles injected into the vision model (zero modification or semi-transparent overlay), multi-round corrections & auto boxes | `image`, `question` required; `items`/`auto_boxes` at least one; `mode`, `alpha`, `corrections` |



| `scan_anomalies` | **Automated anomaly scanning**: tile-based candidate locating → high-res per-candidate verification → report with angle/silkscreen/confidence | `image` required; `target`, `region`, `verify`, `max_tiles` |







Coordinate system: all tools accept `coords="pixel"` (default, measured more accurate with MiMo) or `coords="norm"` (0–1000 normalized); out-of-bounds coordinates are clamped automatically and reported via `clamped: true`.

```toml



# --- MCP: Vision Primitives MCP ---



[mcp_servers.vision-primitives]



command = "python"



args = ['/path/to/vision-primitives-mcp/vision_primitives_mcp.py']



startup_timeout_sec = 60







[mcp_servers.vision-primitives.env]



VISION_API_BASE = "https://api.xiaomimimo.com/v1"



VISION_API_KEY = "sk-your-xiaomi-mimo-key"



VISION_MODEL = "mimo-v2.5"



VISION_OUTPUT_DIR = '/path/to/vision-primitives-mcp/generated'



```







Restart Codex, verify with `vision_health`. Works with any MCP client (Codex, HanaAgent, Claude Code, etc.).

## Example interactive workflow







```text



User: check this screenshot for errors and circle the error locations



Model (Codex):



1. ocr_image("screenshot.png")            # extract text + coordinates



2. locate_object("screenshot.png", "error text region")



3. crop_image("screenshot.png", box)      # crop to inspect detail



4. zoom_region("screenshot.png", box, scale=3)



5. annotate_image("screenshot.png", [{label:"error", box, color:"#ff3b30"}])



   -> returns annotated image path, Codex shows it to the user



```







## Locate methodology: three modes & VLM selection advice (v1.10)







| Mode | Principle | When to use |



|---|---|---|



| `locate_object` (coordinate output) | Model directly outputs pixel/normalized coordinates | General fallback; fine for geometric shapes, 20-70px error on complex elements |



| `som_locate` (number reference) | Overlay numbered marks, model picks a number, recursive crop-and-zoom | **Recommended for models without grounding training (MiMo)**; turns coordinates into a numbering problem |



| `cursor_locate` (interactive search) | Render cursor, model outputs relative offset, visual-feedback convergence | When high precision is needed; relative-offset estimation beats absolute coordinates (GUI-Cursor interactive search) |
| `cv_locate` (CV fallback) | Color segmentation + connected-component centroid / template matching, pure-local pixel-level | **Fallback for simple targets**: solid-color UI elements (click-type), geometric shapes, fixed-template components; limited generalization, use VLM for general targets |







**VLM selection advice (for locate tasks)**: prefer vision models with grounding training — one order of magnitude more accurate than generic VLMs outputting coordinates (evidence: GUI-Actor / SE-GUI / GUI-Cursor papers all identify weak spatial-semantic alignment in text-coordinate generation):







- **First choice Qwen-3-VL-8B**: Qwen3 vision series, continues the grounding-training line (box-token output), mature local deployment



- **Safe fallback Qwen-2.5-VL-7B**: hard evidence for grounding ability (RefCOCO 93.7%), most community validation



- **Avoid Qwen-3.5-9b**: no vision grounding training (measured 210px error); **avoid Gemma4-E4B**: no grounding training track record in Gemma family



- Deployment: load in LM Studio, switch via `VISION_API_BASE` / `VISION_API_KEY` / `VISION_MODEL`; for local thinking models see the minicpm-v-4_5 recommended config (`VISION_DISABLE_THINKING=1` etc.)

## Security notes







- Input images are read-only; never written/modified; uploads go only to the configured MiMo API



- `out_path` is forced inside `VISION_OUTPUT_DIR` to prevent out-of-bounds writes



- API key lives only in local `~/.codex/config.toml` (same as the GitHub token); if leaked, rotate it at the [MiMo console](https://platform.xiaomimimo.com)



- Image size ≤20MB; extension whitelist: png/jpg/jpeg/webp/gif/bmp

## Feature deep-dive







### scan_anomalies — automated anomaly component scanning (v1.1)







One-step "find anomalous components" without manual multi-round operations:







```text



scan_anomalies(image, target="components that are tilted or inconsistent with surroundings",



               region=[x1,y1,x2,y2]?, verify=true, max_tiles=6, overlap=250)



```







How it works:



1. Tile `region` (default: full image) into overlapping blocks (max `max_tiles`), run `locate_object` per block to collect candidates (**full bounding box + rotation angle + all targets**)



2. Merge/dedupe by spatial position (center distance / IoU)



3. With `verify=true`: crop each candidate from the **original** image at high resolution, verify with objective questions (tilt? angle? silkscreen? type), parse into structured verdicts



4. Output candidates sorted "tilted → uncertain → normal"







Measured (2026-08-01, 200MP PCB, region limited to bottom-right): 4 tiles → 3 candidates → auto-verification eliminated 2 → locked the tilted component (A1142C LDO area, ~30° tilt, silkscreen 5C). ~2min total (8 vision calls).







> Known limits: vision models have low recall for "tilted" detection and unstable angle estimates (10°–35° fluctuation); the value of `scan_anomalies` is **automated multi-candidate + per-candidate verification**. Physical verification still recommended. For huge images (e.g. 200MP), raise `VISION_MAX_IMAGE_MB` to the actual file size (default 20MB).







### reason_graph — interactive graphical reasoning protocol (v1.8)







`step` actions: `locate` (with refine) / `measure` (programmatic distance/angle/area, zero API cost) / `annotate` (persist as annotation + overlay) / `semantic` (record semantics) / `hypothesis` / `verify` (virtual annotation verification) / `next` (suggestions). `session` carries primitives/annotations/semantics/hypotheses across rounds.







Measured (mermaid power diagram): locate 2 nodes → programmatic distance 833px → hypothesis "LDO input comes from TD1583" → model verified → `next` suggested further reasoning.







### annotate_infer — virtual annotation + graphical reasoning (v1.5/v1.6)







- `mode=virtual` (default): annotation geometry (box/point/line/arrow/circle/polygon/bubble) injected as coordinate text, **zero modification of the original image**



- `mode=overlay`: semi-transparent annotation overlay (alpha adjustable) sent to the model



- Multi-round corrections: `add / remove / move(delta|to) / resize / set`; auto boxes via internal `locate_object`



- Measured: 200MP PCB with virtual annotations (A1142C tilted LDO + SL2.1S HUB + power arrow) → model correctly inferred the power chain (TD1583→LDO→HUB VCC) and three reliability risks (tilted solder joint / thermal / pins)

## Multi-backend comparison (same benchmark)







| Model | describe/OCR | locate | Notes |



|---|---|---|---|



| MiMo V2.5 (cloud) | excellent | usable (20px after refine) | current recommendation; 15-25s per call |



| qwen3.5-9b (local LM Studio) | excellent (<15s) | **unusable** (210px error, color-position mapping errors) | weak locate; refine fails due to coarse initial box |



| minicpm-v-4_5 (local) | excellent (accurate bbox) | usable (x exact, y systematically ~90px up) | needs `VISION_DISABLE_THINKING=1` |







Conclusion: **cloud MiMo is the best cost/performance vision backend today**; local models are fine for describe/OCR but not for precise locate.







## Performance & known limits







- **Latency**: MiMo is a reasoning-type model; ~15-25s per vision call, ~2min full closed loop. The biggest current drawback



- **Image limits**: ≤20MB; png/jpg/jpeg/webp/gif/bmp; large images auto-downscaled (long edge 2600px, configurable)



- **Locate variance**: sampling-dependent; use `VISION_SAMPLES=3` or `refine` for critical tasks, verify after drawing



- **Network**: automatic 1 retry on connection timeouts/errors







### Why boxes are imperfect (measured root cause)



- MiMo's vision token granularity is coarse (a 200×100 image gets only 18 image tokens) + no dedicated grounding training + sampling variance



- High-contrast regular geometry (circles/color blocks): **0 error**; rounded buttons/text/PCB component edges: 20-70px off



- Built-in mitigations: `refine` two-stage refinement, `VISION_SAMPLES` median-of-samples, `scan_anomalies` per-candidate verification, coordinate clamping

### v1.9.1 (2026-08-02) — MCP response protocol fix (strict-client compatibility)







- **Fix**: tool response frames from `_text_result` lacked `jsonrpc` and `id` fields; strict MCP clients (e.g. HanaAgent) could not match responses to requests, so every tool call appeared to "time out" (the tool had actually completed and returned, but the response was dropped). Response frames now carry `jsonrpc` + `id`, consistent with initialize/ping/error responses



- Impact: Codex tolerates missing id, which is why it never surfaced; fix is backward-compatible, no interface changes



- **HanaAgent full-chain verification** (after fix): `vision_health` 0.18s, `describe_image` cache hit instant, `ocr_image` 23s, `locate_object` 4.7~6.3s, all returning normally



- **Cross-validation baseline** (programmatic ground truth, PIL pixel-level checks):



  - `locate_object` red circle: 43.3% red pixels inside box, center offset 64px — box contains the target, coarse locate usable, consistent with the known "20~100px error" finding



  - `locate_object` green triangle: 14.2% green pixels inside box, center offset 97px (box shifted bottom-right)



  - `ocr_image` position: near-exact x hit, y ≤15px error; text content 4/4 correct
